# 會議紀要方法論（內建自 asr-minutes 技能）

來源：repo 根目錄 SKILL.md。本檔為 App 自動摘要版——摘要結果直接寫入會議記錄檔，
沒有對話可附帶說明，故刪去「對話中另附」類段落（詞彙表來源聲明、詞彙表增量、交付後說明、
範本對齊、中英雙版），其餘紀律照原文。修改本檔即改變所有摘要的寫法。

## 一、先修復聲學誤聽，再整理紀要

輸入形態判斷：
- 生逐字稿（大量同音錯字、無標點長串）→ 完整聲學修復。
- 已初步校正的逐字稿 → 殘錯校驗：只掃漏網誤聽，重點看新出現的變體。
- 非語音材料（紀要草稿、討論摘要、流水帳）→ 跳過修復，直接整理紀要。

事實源鐵律：逐字稿是唯一事實源。背景、前情提要、術語表只用來理解與還原專名，不得當作紀要素材。
逐字稿無法定位到的結論、負責人、期限、數字，不得寫入。

### 1.1 訂正紀律（三段式，不得跨類升降）

第一類 孤立詞、上下文不足：保留原文，標「（原文，待确认）」或「[语焉不详]」，不做推定。
多人搶話、快速報數導致的破碎片段不「順」成完整句（那是替發言人編造內容）。

第二類 貫穿全場的主體專名：凡全場高頻出現、明顯是機構／公司／系統主體的專名，不得因置信不足而省略，
也不得以「合作方」「某厂商」抹去。以下列形態保留在正文：
- Northwind Capital（转写为 NORTH WIN／NOSWIND）
- 置信較低時：合作方（转写为 NORTH WIN／NOSWIND，依会议语境推定为 Northwind Capital，待确认）

推定方法：先用會議主題把候選空間收窄，再與聲學形態比對。例如全場討論會議錄音、語音轉寫準確率
 → 候選為「語音辨識模型」；全場並列 Whisper、SenseVoice → 候選為「開源 ASR 模型」，
即可推定 PARA FORMER 為 Paraformer。候選空間無法收窄到可辨識程度時，退回第一類。
推定不等於事實：僅靠主題＋聲學得到的結果一律標「待确认」。

第三類 術語表已收錄，或上下文高置信：直接還原為正確寫法，不加標記。
人員／系統代號（ABC、XYZ 之類）無法確認指代時仍歸第一類。

### 1.2 英語場次

- 逐段對照術語表的英語高頻誤聽。
- 監管術語（CFD／MTF／ESMA／MiCA／PEP）誤聽形態常與其他縮寫撞形（如 CFT），按業務語境判定，不機械替換。
- 口語估數（「maybe twenty five」）是隨口估計，不得寫成清單數量或確定值；「five criterias ... a couple of things」
  中的數字是舉例而非規格，寫「若干项」。

### 1.3 數量與歸屬紅線

- 未標明單位的數字（如「three or four」）保留原文並註明「单位未明确」，不得用評價性語言（「占比极低」）替讀者補完解讀。
- 逐字稿為單一說話人標籤時，不逐句標註歸屬；無法判定說話方的關鍵陳述（比例承諾、責任劃分），
  寫成無主語句並註明「发言人归属无法从逐字稿确定」。
- 不得將對話中的假設、舉例、反問寫成已達成的結論。

## 二、紀要整理

### 2.1 禁止自造固定樣板

不得用固定章節名硬套。以下是「會議沒討論到就不該有」的佔位式章節，禁止自行使用：
「待确认事项」「后续行动计划」「遗留问题」「存在分歧事项」「已达成共识事项」「讨论要点」「风险与依赖项」。
章節名稱從材料中提煉，準確描述該段討論內容：
- ❌「三、讨论要点」「八、讨论要点/后续事项」→ 空泛佔位
- ✅「三、自动化补币可行性评估」→ 精準描述

若前情提要中明確給了要對齊的章節骨架，可沿用其章節名，各節以本場實際事實填實，未討論到的節不填。

### 2.2 章節數量由內容決定

讀完材料後列出「這場會議實際涵蓋哪些議題」，每個議題一個精確標題。
沒討論到的議題章節不存在，不留空殼，不填「暂无」。

### 2.3 已確認與未確認嚴格分開

- 已明確達成共識的結論 → 陳述句寫入正文。
- 仍在討論、有前提條件、未達成共識的 → 明確標記狀態，不假裝已定論。
- 兩類內容不混入同一段落。
- 一場會議可能同時有大量共識與大量待定，不得因討論有爭議就整體判為「未形成决议」。

### 2.4 重點優先編排

先讓「這場會議決定了什麼」一眼可讀，其次才是敘事完整性。決策／範圍／流程／邊界／待辦是主力；
對話順序、語氣細節、未定音譯降為輔助。

1. 決定是「章節式決策文件」還是「流水紀要」：能歸結為若干條已確認範圍、流程、共識與條件性結論 →
   章節式決策文件，沿「範圍 → 流程 → 各專業議題（KYC/AML/法務…）→ 定位 → 待辦」鋪陳，不用講話時間順序。
   只有重點本質是逐步討論、無可抽出的決策骨架時，才退回時間軸紀要。
2. 已確認的結論、範圍、流程、規則清單優先條列：
   - 流程用編號步驟（1. 2. 3.），一步一件事；資金／資料流動點出方向與時序。
   - 範圍／邊界／並列規則用項目符號，一項一態。
   - 分支流程（如「KYC 已完成 vs 未完成」）拆成兩類分別陳述。
   - 章節標題即決策標題（「一、本期范围」「二、项目定位」），掃標題即掌握會議決定。
3. 連續散文是補充手段，不是預設：一行一句完整陳述，交代因果與前提（如「反洗钱理由：…」「因此…」）。
   技術闡述、授權細節、前提說明若與核心決策分離，移到該節後段或文末「补充说明」。

禁止將對話順序照抄為章節順序。

### 2.5 禁用「與會者」及一切等效泛稱主語

「与会者」「出席者」「参会人员」「会议成员」「讨论方」「相关人员」等不得作句子主語。替代：
- 已形成結論 → 直接寫結論，無主語。
- 需標明來源方 → 用具體方名（「供应商」「风控侧」「技术侧」）。
- 需標明具體發言人 → 用人名。
- 無法判定來源且非結論 → 無主語句。
此規則無例外。

### 2.6 行動項

逐字稿明確指名某人負責某事 → 在對應章節用項目符號寫「负责人 做什么（期限）」，期限未提則不寫期限。
只有泛泛的「後續要做 X」而無負責人 → 寫入對應章節正文。
提報路徑、分工流程類內容用項目符號逐條列（見範例「五、需求提报路径」）。

### 2.7 格式規範

- 不寫文件標題行，直接從「一、」開始。
- 章節標題獨立成行：「一、[章节名]」；子章節「4.1 [子节名]」。純文字，不加粗、不加 #。
- 第一節交代背景（為何開這場會、問題現況、頻率或規模、此前經過）；決議集中在「决议」一節，
  可用「做什么／不做什么／设计要求／后续要求」等子節拆開。
- 正文一行一個完整陳述；並列項目才用「- 」，不用表格、不用粗體。
- 日期寫 YYYY/MM/DD。
- 禁止「暂无」「待补充」「如适用」等佔位文字。

### 2.8 脫敏

未指定時保留原文。前情提要要求脫敏時以 [甲方] [乙方] [产品名] [姓名] [UID] 統一替換，不用 XXX 或 ***。

## 三、格式範例（只學結構與行文，內容一律來自本場逐字稿，不得照抄範例的事實）

一、需求背景
用户在 App 内更换绑定手机号后，旧号码仍占用原会员资料，新号码只能重新注册，积分与订单记录无法带过去。
发生频率高——客服每天约收到五六起相关咨询。
参照同业 App 的做法，其允许用户在验证身份后把会员资料迁移到新号码。本次会议讨论能否支持该功能及潜在风险。
本需求此前提报时曾被驳回，故召开本次会议。

二、法务立场：会员身份与登录账号是两个层级
法务明确了本次讨论中最核心的概念区分：
- 会员（身份）：一个人只有一份会员资料。
- 登录账号：可以更换，法务从未限制更换次数。
关键要求：账号更换前后的记录必须能串起来，不能出现两份互不关联的会员资料。

三、技术侧说明
现行"一个手机号只能对应一个会员"是当初按法务要求实现的限制，改为可迁移在技术上可行。

四、决议
4.1 做什么
支持会员资料从旧号码迁移至新号码。用户自主发起，验证本人身份后同意迁移，平台不代为操作。
4.2 不做什么
一份会员资料同时绑定多个号码，本次不做。
4.3 设计要求
- 需设计迁移后旧号码的限制条件——能否继续登录、能否领取优惠。
- 后台是否增加审核环节，视同业做法评估后决定。

五、需求提报路径
- 由业务侧提报需求，产品设计方案时与法务、客服沟通评估。
- 技术侧评估实现方式、影响范围与改造周期。
